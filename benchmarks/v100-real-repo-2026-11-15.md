# Real repository/tool workloads: IQ3_XXS versus NVFP4-QAD

## Result

**NVFP4 did not deliver 90+ tok/s on this workload.** It measured 55.6 tok/s
on matched repository continuations and 59.75 tok/s in live read/search
loops. The earlier synthetic 94.74 tok/s result is not a daily-use estimate.
There is no speed-based reason from these runs to switch the daily service
to NVFP4.

| Workload and metric | Current IQ3_XXS | NVFP4-QAD |
| --- | ---: | ---: |
| Matched repository replay: median decode | 66.5 tok/s | 55.6 tok/s |
| Matched repository replay: median first output | 6.062 s | 10.927 s |
| Matched repository replay: median complete HTTP turn | 12.353 s | 15.615 s |
| Live read/search loops: median decode | 71.1 tok/s | 59.75 tok/s |
| Live read/search loops: median first output | 4.467 s | 6.780 s |
| Live read/search loops: median complete HTTP turn | 7.414 s | 10.269 s |

The matched replay table uses 45 equal-fresh-token pairs. One additional
pair had a cache miss in only one model and is kept in the data but excluded
from that table. All 46 replay requests per model give decode medians of
66.75 and 55.7 tok/s, respectively.

The live loops take model-selected tool paths, so their rows are not equal
work. Their latency medians describe observed use, not paired speedup
ratios. Neither table is a model-quality score.

## What ran

157 measured streamed requests:

- 92 controlled repository continuations: 23 turns, two models, two rounds.
- 65 live-loop requests: the model chose read/search calls, the runner
  executed them on real source files, and the results were returned to it.
- 36,795 generated tokens in total. All requests, including short replies
  and length-capped output, remain in the data.

The replay uses the existing `tools/agent_turns_bench.py` **repo** workload,
not its synthetic-word `agentic` workload. Five sessions inspect server
options, expert caching, installer RAM detection, CUDA kernels and the
Python tokenizer. Tool results contain actual repository text. English and
French tasks are included. The histories are fixed between arms; generated
replies are not fed into the next replay request.

The separate live loops investigate native expert dispatch, streamed tool
arguments and MTP/verification. Each starts with a real source excerpt.
The model then chooses `read_file` or `grep`; reads and searches execute
against the repository. Its actual replies and tool results become the
next prompt. The tools cannot edit files or execute shell commands.

Actual total prompt lengths ranged from 2,187 to 121,026 tokens. Actual
new reads ranged from 31 to 52,128 tokens. The longest reused prefix was
71,779 tokens. These are measured counts, not requested target lengths.

## Controls

- Same installed engine for both models:
  `ab7867155e8d309ef1014403cd534df6f7ddaf8782fe0dcfad7510451bbed87b`.
- Same server file as the daily service. Its hash is in the metadata.
- Two Tesla V100-PCIE-16GB cards, 175 W each, driver 580.178.04,
  Ryzen 5 3600. GPU0 uses PCIe Gen3 x4; GPU1 uses x16.
- Existing model-specific daily profiles, common systemd tuning, GPU order
  `[0,1]`, split 16, MTP 4 and the existing verification cap.
- Shared request sampling: temperature 1, top-p 0.95, top-k 20, min-p 0.05,
  seed 1234, low reasoning effort and zero reasoning budget.
- Up to 512 generated tokens per request, not padded to that size.
- Model order: IQ3, NVFP4, NVFP4, IQ3. Each process had its own conversation
  store and profile-save destination. Production profile files were read,
  not overwritten by the test arms.
- The same source revision generated every fixed replay prompt:
  `ea920318ec4009a1e16efde755b85777ba638f51`.
- Benchmark servers bound only to loopback, without copying the service key.

## Variation and limits

NVFP4's repository decode median was 55.6 tok/s in round one and 55.8 in
round two. IQ3 was 71.9 and 60.1. That IQ3 drift is real; these runs do not
identify its cause. GPU temperatures were sampled only before the run
(41/45 C) and after restoring the service (54/72 C). Continuous thermal
telemetry was not collected, so no no-throttling claim is made.

The aggregate generated-tokens / decode-time rates across **all** requests
were 60.97 tok/s for IQ3 and 56.49 for NVFP4. These differ from per-request
medians because reply lengths and slow requests have different weights.
Do not mix the two statistics or use the highest individual rate as a
model's daily speed.

The live-loop runner limits each task to eight requests and each reply to
512 tokens. Several tasks reached a limit or ended without a complete
answer. The raw `completed` flag means only that a final protocol response
was reached, not that the answer was correct. No task-success, coding
quality or quantization-quality conclusion follows from it.

This is a controlled repository workload plus real tool execution, **not a
replay of the user's private production conversations**. It is much more
representative than repetitive synthetic prompts, but it cannot guarantee
a speed for every application or context length.

The first startup attempt found port 8090 occupied. No request was measured
on that attempt and the existing listener was not stopped. The successful
run selected an unused loopback port.

## Reproduction and evidence

- [Every measured request, profile, hash and task outcome](../bench/results/2026-11-15-real-repo/measurements.json).
- [Standalone experiment runner](../bench/results/2026-11-15-real-repo/run.py).

The runner takes a local JSON file with `iq3` and `nvfp4` configuration
objects, plus a fresh output directory. Use the current pipeline config
for IQ3 and the existing QAD service config for NVFP4. Remove API keys;
keep the measured profile arguments, tokenizer, vision reservation, GPU
order and common tuning. The exact engine arguments and tuning used here
are recorded under `engine_profiles` in the measurements.

```sh
STRATA_LIVE_REPO=/path/to/daily/checkout python \
  bench/results/2026-11-15-real-repo/run.py \
  /path/to/private-free-model-configs.json /tmp/real-repo-run
```

The script temporarily stops `strata-v100.service` if it is active and
restarts it in `finally`. It terminates only its own benchmark process
groups. Run it only when that service may be interrupted.

After this run the original service was active, with its original config
and installed engine. An authenticated arithmetic smoke returned `17` for
`9 + 8`, with finish reason `stop`. No model switch was deployed.
